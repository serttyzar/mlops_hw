# Семь дефектов процесса выпуска

Продолжение ДЗ 6+7. Исходный прототип сохранён коммитом `732ddae`,
исправления ядра — `64ac195`. Машиночитаемая таблица с причинами,
командами, тестами и коммитом — [defects.csv](../defects.csv).

Для каждой причины новый регрессионный тест запущен на исходной и исправленной
версиях. [Красный журнал](logs/integration-before.log) содержит падения по
поведению; [итоговый зелёный журнал](logs/check-after.log) — успешные проверки.
Старые `tests/` ДЗ 6+7 и приложенные 13 тестов выпуска не изменены.

## 1. Кеш не учитывал содержимое данных и настройки подготовки

**В чём был дефект.** `release.cache_key()` вычисляла SHA256 только от строки
пути. Байты файла и весь `config` игнорировались. После изменения `input.txt`
по прежнему пути подготовка читала устаревший результат и печатала `CACHE_HIT`.

**Как исправлено.** Ключ считается от канонического JSON с хешем байтов входа
и полным конфигом. Поэтому одинаковые данные в разных путях имеют один ключ,
а изменение tokenizer revision, template hash, max_length или версии кода
подготовки инвалидирует кеш. Результат сохраняется на диск; задача подготовки
Prefect использует этот же ключ и `persist_result=True`.

**Чем подтверждается.** `test_cache_recovery_and_changed_input`: намеренный
сбой после подготовки, повтор в другом процессе, изменение байтов и четырёх
настроек. На исходной версии после изменения данных оставался `CACHE_HIT`;
после исправления появляется `PREPARED`. В отдельном Prefect-опыте после сбоя
состояние `Cached`, после изменения входа — `Completed`:
[восстановление](logs/flow-recovery.log), [инвалидация](logs/flow-invalidation.log).

## 2. Неполный или чужой отчёт разрешал выпуск

**В чём был дефект.** `validate_release()` проверяла только truthiness поля
`passed`. Строка `"false"` считалась разрешением. Не проверялись завершённость
оценки, принадлежность отчёта модели, runtime, обязательные поля и метрики.
Запуск с `report-incomplete.json` или отчётом A для модели B менял указатель.

**Как исправлено.** Нужны `status='complete'`, именно boolean `passed=True`,
непустой evaluation run ID, корректная схема manifest, совпадающие model ID и
четыре хеша. Хеш runtime пересчитывается. Accuracy и format rate должны быть
конечными числами в [0,1]; bool, строки, NaN и Inf запрещены.
Для настоящего выпуска `gate_bridge.py` дополнительно пересчитывает метрики
по raw-ответам и вызывает неизменённый полный `quality_gate` из ДЗ 6+7.

**Чем подтверждается.** `test_incomplete_and_foreign_reports_preserve_pointer`
проверяет ненулевой exit code и одинаковые SHA256 указателя до/после отказа.
Приложенные контрактные тесты проверяют missing, несовпадения, NaN/Inf и типы.
Реальный кандидат также отклонён полным gate; baseline сохранена:
[опыт публикации](../metrics/real-publication.json).

## 3. Указатель перезаписывался без атомарной замены

**В чём был дефект.** `publish()` напрямую вызывала `target.write_text()`.
Такая запись могла обрезать прежний файл до завершения новой записи.
В тесте с ошибкой `os.replace` исключение вообще не возникало: замены не было.

**Как исправлено.** После проверки отчёта JSON записывается во временный файл
рядом с целевым. Выполняются `flush`, `fsync`, затем `os.replace` и `fsync`
каталога. Временный файл удаляется при ошибке, исключение передаётся вызывающему
коду. Отказ gate не начинает запись. Повтор одинакового выпуска сохраняет байты.

**Чем подтверждается.** `test_rejection_and_disk_error_preserve_pointer`:
отказ отчёта и смоделированная ошибка замены сохраняют прежний SHA256,
временные файлы не остаются. Настоящий диск для опыта не заполнялся.
Тот же контракт проверяет исходный `test_failed_atomic_replace_preserves_previous_bytes`.

## 4. Повтор выпуска размножал события публикации

**В чём был дефект.** После каждого запуска `lab.run()` безусловно дописывала
строку в `publications.jsonl`. Два процесса с одним выпуском давали две записи.
Не было устойчивого идентификатора выпуска и восстановления после сбоя между
изменением указателя и записью события.

**Как исправлено.** В `publication.py` идентификатор выпуска считается по
manifest и связанному отчёту: модель, runtime и оценка участвуют в идентичности.
События дедуплицируются; журнал целиком обновляется атомарно. До изменения
указателя сохраняется pending-intent. Если процесс падает после замены указателя,
следующий запуск завершает запись события. Попытки пишутся отдельно в
`attempts.jsonl`. Механизм рассчитан на одного писателя.

**Чем подтверждается.** `test_identical_release_in_two_processes_has_one_event`
на исходном коде находил две записи, на исправленном — одну. Дополнительные
`test_crash_after_pointer_recovery_is_idempotent` и
`test_journal_write_failure_can_recover` проверяют восстановление.
[Prefect-журнал](logs/flow-journal-recovery.log) содержит `RECOVERED`;
[сводка опытов](../metrics/flow-experiments.json) сохраняет единственное событие
после сбоя, восстановления и ещё одного повтора.

## 5. Сервис объявлял готовность до прогрева

**В чём был дефект.** `ServiceState.ready` сразу устанавливалась в `True`.
`/ready` и `/generate` могли возвращать 200, хотя `warmup_finished` ещё не был
установлен. Health и готовность обслуживать запросы не различались.

**Как исправлено.** Начальное состояние — не готов. Готовность выставляется
после проверки артефакта, загрузки backend и завершения прогрева. Для настоящей
модели выполняется warmup-генерация. До готовности `/ready` и корректный
`/generate` возвращают 503; `/health` подтверждает жизнь процесса.
Общее состояние используется stdlib-адаптером и FastAPI через lifespan.

**Чем подтверждается.** `test_http_readiness_blocks_generation_until_warm`
обращается к настоящему HTTP-серверу и проверяет 503, отсутствие вызовов backend
до прогрева и последующий успешный ответ. Этот тест проходит на обоих
транспортах. [Реальный smoke](../metrics/api-smoke.json) также содержит переход
health=200/ready=503 → ready=200.

## 6. Метаданные ответа не соответствовали загруженной модели

**В чём был дефект.** Backend загружался один раз, а `generate()` перечитывала
`accepted.json` для полей ответа. После публикации B процесс продолжал считать
на A, но сообщал `model_id` и runtime версии B.

**Как исправлено.** Ответ получает идентификатор и runtime hash из фактически
загруженного backend. Принятый manifest читается как снимок при запуске.
Изменение файла не меняет модель в памяти: для загрузки новой версии требуется
управляемый перезапуск, перед ним снова проверяются файлы и связанный допуск.

**Чем подтверждается.** `test_http_loaded_version_restart_and_rollback`:
старт на A, публикация B другим процессом, ответ A до рестарта, B после рестарта,
затем выпуск ранее принятой A и возврат к A после нового запуска. Опыт работает
через настоящие HTTP и subprocess со STUB-версиями. Для настоящей baseline
отдельный [restart smoke](../metrics/api-smoke-restart.json) подтверждает загрузку
того же принятого model ID/runtime; отклонённый адаптер не выдаётся за принятую модель.

## 7. Некорректный запрос запускал вычисление

**В чём был дефект.** `generate()` передавала prompt и лимит в backend без
предварительной проверки. Пустой prompt, нулевой/чрезмерный лимит, строка или
boolean могли получить 200 и увеличить счётчик вычислений.

**Как исправлено.** До вызова генератора проверяются JSON-объект, допустимые
поля, непустой строковый prompt и его длина, целочисленный лимит без bool.
Ограничены размер тела и число входных токенов. Stub поддерживает 1..32 новых
токена; настоящая модель — только оценённый лимит 32. Ошибки дают 4xx.
Число одновременно выполняемых backend-вызовов ограничено одним.

**Чем подтверждается.** `test_http_invalid_requests_do_not_call_backend`
сравнивает `/debug.calls` до и после неправильных запросов, затем проверяет
валидный запрос. На исходной версии были 200 и лишние вызовы; исправленные
stdlib/FastAPI возвращают 4xx без вычисления. В реальном smoke все пять
неправильных запросов получили 400, а calls осталось 1 → 1; единица — warmup.
