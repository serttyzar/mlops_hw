# Разбор пяти дефектов

Каждый дефект: где был, как проявлялся, почему его не видно без специальной
проверки, как исправлен и каким числом исправление подтверждено.

Общая черта всех пяти: **ни один не роняет пайплайн**. `dvc repro` зелёный,
стадии отрабатывают, файлы на месте. Портится не работоспособность, а
достоверность результата — и заметить это можно только проверкой, которая
ищет именно это.

---

## Дефект 1. Данные утекают в git, выгружать их некуда

**Где:** `.gitignore` и `.dvc/config`.

**Что было.** В `.gitignore` перечислены `__pycache__/`, `.venv/`,
`dvc_remote/` — и ни слова про `data/`. В `.dvc/config` только
`[core] autostage = true`, ни одного remote.

**Как проявлялся.** Первый же `git add . && git commit` кладёт в историю весь
`data/`. На текущем v2 это **44 МБ в пяти JSONL**:

```
raw.jsonl    15 217 925 байт
clean.jsonl  15 294 641
train.jsonl  12 241 968
val.jsonl     1 486 694
test.jsonl    1 489 263
```

Дальше это не вычищается без перезаписи истории, и на каждой новой версии
датасета репозиторий растёт ещё на столько же. Вторая половина дефекта тише:
без remote `dvc push` выгружать некуда, то есть DVC хранит данные только в
локальном кеше. `dvc.lock` ссылается на хеши, которых нет ни у кого, кроме
автора, — воспроизвести чужой прогон нельзя.

**Почему незаметно.** DVC работает и без remote: `dvc repro` считает,
`dvc.lock` пишется, всё зелёное. Проблема всплывает только когда репозиторий
попадает на другую машину.

**Как исправлено.**

* В `.gitignore` добавлены `data/`, а также `.DS_Store`, `*.bak`, `*.orig`
  (последние два — рабочие файлы `tests/check.sh`, которые иначе доезжают до
  ревью).
* Настроен remote: `dvc remote add -d local ../../dvc_remote`. Он **вне
  репозитория** — remote внутри отслеживаемого дерева не решал бы задачу.

**Подтверждение.**

```
git ls-files data/ | wc -l   →  0
dvc remote list              →  local  /Users/.../hw3/dvc_remote  (default)
dvc push                     →  5 files pushed
du -sh ../dvc_remote         →  44M
```

Проверка 1 в `tests/check.sh` — зелёная, включая пункт «все артефакты из
`params.paths` объявлены в `outs` dvc.yaml».

## Дефект 2. Смена версии данных не пересчитывает пайплайн

**Где:** `dvc.yaml`, три разных места.

**Что было.**

1. У стадии `collect` **не было секции `params`** вообще и не было источника
   в `deps` (на месте источника стоял `TODO`).
2. У стадии `clean` в `deps` **не было `data/raw.jsonl`** — её собственного
   входа. У `diversity` и `split` вход (`data/clean.jsonl`) объявлен,
   у `clean` — нет.
3. У стадии `split` в `outs` был только `data/train.jsonl`; `val` и `test`
   отсутствовали.

**Как проявлялся.** `python scripts/set_version.py v2 && dvc repro` →
`Stage 'collect' is cached - skipping run`. Артефакты остаются от v1.

Второй слой оказался хитрее первого и всплыл только после починки первого.
После добавления `params: [collect, paths.raw]` стадия `collect` честно
пересчиталась и выдала 4000 строк вместо 2000 — а `clean` сообщила
`didn't change, skipping` и отдала закешированный `clean.jsonl` от v1.
Замер ровно в этот момент:

```
v1 clean md5 7a3a4c4d...  raw.jsonl 2000 строк
v2 clean md5 7a3a4c4d...  raw.jsonl 4000 строк   ← raw обновился, clean нет
```

Это худший вид поломки из пяти: пайплайн не падает, метрики пишутся,
`dvc.lock` обновляется — и всё это про данные, которых в `clean.jsonl` нет.

Третий слой: `val.jsonl` и `test.jsonl` не были объявлены выходами, значит
не версионировались, не уезжали в remote и не восстанавливались по `dvc.lock`.
Тест, которого нет в истории, нечем воспроизвести.

**Почему незаметно.** DVC сравнивает только то, что ему объявили. Незаявленная
зависимость — это не ошибка конфигурации, которую он мог бы заметить, а
утверждение «результат от этого не зависит», и DVC ему верит.

**Как исправлено.**

```yaml
collect:
  deps:
    - ../../datasets/amasum/shards/0000.parquet
    - ../../datasets/amasum/shards/0001.parquet
    - src/collect.py
    - src/config.py
    - src/textnorm.py
  params:
    - collect
    - paths.raw
  metrics:
    - metrics/collect.json: {cache: false}

clean:
  deps:
    - data/raw.jsonl        # ← вход стадии
    - ...
  params:
    - clean
    - paths.raw             # ← путь к входу тоже параметр
    - paths.clean

split:
  outs:
    - data/train.jsonl
    - data/val.jsonl        # ←
    - data/test.jsonl       # ←
```

Шарды обеих версий перечислены в `deps`, хотя v1 использует только первый:
`dvc.yaml` статичен, а `collect.version` меняется. Лишняя зависимость стоит
лишнего пересчёта; пропущенная стоит артефакта, собранного неизвестно из чего.

**Подтверждение.**

```
v1: clean.jsonl 7a3a4c4d, raw 2000 строк, clean 1996
v2: clean.jsonl 69403532, raw 4000 строк, clean 3981
```

Проверка 4 зелёная. `dvc metrics diff` показывает `rows_written 2000 → 4000`,
`rows_out 1996 → 3981`, `groups 249 → 321`.

## Дефект 3. Сплит по строкам вместо сплита по группам

**Где:** `src/split.py`, функция `row_split`.

**Что было.**

```python
def row_split(count, ratios, seed):
    order = list(range(count))
    random.Random(seed).shuffle(order)   # перемешиваются СТРОКИ
```

Выдающая деталь: в `main()` считался словарь `sizes` — размеры групп, — и
дальше нигде не использовался. Группы считали, но не применяли.

**Как проявлялся.** Строки одной группы разъезжаются по train и test.
В этом датасете группа — товарная полка: у товаров одной полки общий словарь,
похожие формулировки плюсов и минусов и пересекающиеся наборы отзывов
(«easy to clean», «great value for the price»). Обучившись на половине полки,
модель на второй её половине показывает завышенное качество — и это не
обобщение, а память.

**Замер на текущем `clean.jsonl` (1996 строк, 249 групп):**

| | групп в train и test одновременно |
|---|---|
| было: сплит по строкам | **74** |
| стало: сплит по группам | **0** |

То есть 74 из 249 групп — почти треть — находились по обе стороны границы.

**Почему незаметно.** `near_dup_pairs` между train и test равен **0 в обоих
случаях**: товары-то разные, дословных парафразов нет. Проверка контаминации
по тексту дефект не ловит — его видно только на уровне групп. Ровно поэтому
`report()` в `src/contamination.py` меряет три вещи, а не одну.

**Как исправлено.** `row_split` заменена на `group_split`: метки раздаются
**целым группам**. Раздача жадная — группы идут от крупных к мелким (крупной
труднее найти место, оставлять её напоследок значит промахнуться по долям),
каждая уходит в сплит с наибольшим недобором. Порядок равных по размеру групп
задаёт seed, а не алфавит: иначе сплит определялся бы тем, как называется
товарная полка.

**Подтверждение.** Доли не пострадали, несмотря на неделимость групп:

```
v1: train 1597 / val 200 / test 199   → 0.8001 / 0.1002 / 0.0997
v2: train 3185 / val 398 / test 398   → 0.8001 / 0.1000 / 0.1000
```

`scripts/check_contamination.py`: пересечение по id 0, по тексту 0,
по группам 0, near-dup пар 0. Проверка 5 зелёная.

## Дефект 4. Дедупликация только точная

**Где:** `src/clean.py`, шаг 5.

**Что было.**

```python
# 5. TODO: сюда просится ещё один шаг дедупликации.
near: set[int] = set()
```

Пустое множество, которое дальше честно попадало в метрику
`dropped_near_dup` — то есть метрика всегда показывала 0 и выглядела как
результат проверки. При этом рабочая функция `near_duplicates()` в
`src/dedup.py` была на месте и просто никем не вызывалась.

**Как проявлялся.** Точная дедупликация сравнивает нормализованные тексты
побайтово. Переформулировка, другая нумерация вариантов или лишний пробел
дают другой ключ и проходят её насквозь. Пара почти одинаковых примеров
остаётся в датасете дважды, а потом расползается по train и test.

**Почему незаметно.** Метрика `dropped_near_dup: 0` неотличима от честного
нуля. Именно поэтому в `check.sh` подкладывается синтетическая пара, где
почти-дубль заведомо есть.

**Как исправлено.** Шаг 5 вызывает `near_duplicates()` по нормализованному
тексту пользовательской реплики, MinHash+LSH, параметры из
`params.clean.near_dup` (4-словные шинглы, 64 перестановки, порог Жаккара
0.85). Шаг идёт **после** точной дедупликации, и индексы считаются по уже
прореженному списку — иначе они указывали бы не на те строки.

**Подтверждение.**

| | v1 | v2 |
|---|---|---|
| убрано точной дедупликацией | 1 | 3 |
| убрано near-dup **дополнительно** | **3** | **16** |

На v2 шестнадцать почти-дублей, которых точная дедупликация не видела.
Число небольшое — источник разнообразен, это разные товары; попадаются
варианты одного товара (другой цвет, другой размер) под разными ASIN с почти
одинаковыми отзывами. Именно их шаг и ловит.

Синтетическая проверка 2 в `check.sh`: `dropped_near_dup = 1` на подложенной
паре, где отличаются только нумерация вариантов и пробелы.

## Дефект 5. Гейт разнообразия — не гейт, а предупреждение

**Где:** `src/diversity.py`, `main()`.

**Что было.**

```python
if failed:
    # TODO: гейт или отчёт? ...
    print("diversity: предупреждение — " + "; ".join(failed))
```

Стадия печатала нарушения и **возвращала нулевой код**. Пайплайн ехал дальше.

**Как проявлялся.** Вырожденный набор — 1200 строк с одним системным промптом,
одной темой и ответами одной длины — проходит схему (строки валидны),
дедупликацию (тексты различаются), сплит и контаминацию. Каждая из этих
стадий смотрит на строки **по отдельности**, а вырожденность — свойство
набора целиком. Diversity — единственная стадия, которая это видит, и она
об этом только сообщала. Обучение на таком наборе сходится быстрее обычного,
и модель выучивает шаблон вместо задачи.

**Как исправлено.** Нарушение порога → `raise DiversityError`. Метрики
записываются **до** исключения и переживают падение, иначе чинить пришлось бы
вслепую.

Вторая, менее очевидная часть: нарушения печатаются **по одному в строке**,
а не через `"; "`. Разбирать их предстоит по отдельности, и число нарушений
должно читаться из лога как число строк, а не как единица.

```python
raise DiversityError(
    f"{paths['clean']}: набор вырожден, нарушено порогов {len(failed)} "
    f"(подробности в {mpath})\n"
    + "\n".join(f"  - {v}" for v in failed)
)
```

**Подтверждение.** На вырожденном наборе из проверки 6 стадия падает
(`DiversityError`, ненулевой код возврата) и называет **6 нарушенных
порогов**:

```
DiversityError: data/_check/degenerate.jsonl: набор вырожден,
нарушено порогов 6 (подробности в metrics/diversity.json)
  - системных промптов 1, нужно ≥ 3 — модель заучит единственную формулировку как константу
  - групп 1, нужно ≥ 50
  - крупнейшая группа занимает 100.0% (порог 10%): «одна-единственная тема - 2025»
  - разброс длин ответа p90/p10 = 1.0, нужно ≥ 1.6 — ответы одной длины выдают шаблон
  - 100.0% ответов имеют одну и ту же длину (порог 25%)
  - 99.7% ответов дословно повторяют друг друга (порог 30%)
```

Сама проверка 6 засчитывает 4 из шести: она ищет `grep -cE` по четырём
формулировкам и считает **строки**. Это и есть причина, по которой печать
через `"; "` не годилась бы: шесть нарушений в одну строку дают `grep -c` = 1,
и проверка провалилась бы с формулировкой «гейт упал, но не объяснил,
что именно не так».

Проверки 6 (падает на вырожденном) и 7 (пропускает нормальный) — обе зелёные.
На реальном v2: 3981 строка, 5 системных промптов, 321 группа
(крупнейшая 6.0%), p90/p10 = 1.88, одинаковой длины 0.8%, дословных
повторов 0%.

Пороги `diversity` в `params.yaml` **не менялись** ни разу. Под порог
подгонялись данные — в частности, `collect.max_group_share` = 0.06 при
проверочном пороге 0.10 (см. `docs/datasheet.md`, §2.4).
