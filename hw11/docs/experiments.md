# Протокол опытов

Это план и реализация воспроизведения. Факт выполнения определяет только
results/cluster-*/ с requests.jsonl, событиями и успешными checks.jsonl.
Локальные ASGI-проверки не подтверждают работу Kubernetes.

## A — прогрев и выпуск

Гипотеза: HTTP listener не гарантирует прогретый backend. Режим brokenProbes
намеренно отвечает 200 на startup/readiness во время прогрева. Из чистого
состояния подаём один и тот же поток 40 с, 2 req/s, две части. До исправления
требуем хотя бы один backend_unready; после — ни одного. До появления готовых
endpoints исправленный вариант может давать транспортные ошибки: это не
нулевой простой свежего старта, а корректный запрет трафика непрогретому Pod.
Ready и EndpointSlice сохраняются каждые ~2 с, запросы журналируются по Pod.

Для штатного rollout: две реплики, concurrency=2, прогрев 20 с, minReadySeconds=5,
maxUnavailable=0, maxSurge=1. Один 64-частный ответ с интервалом 0,5 с начинается
на старом Pod до обновления. Нагрузка 75 с, 1 req/s, две части. Приёмка требует
завершения ВСЕХ запросов, включая длинный: не только отсутствия HTTP 5xx.
preStop даёт 5 с на распространение удаления endpoint, затем включает drain.
Uvicorn ждёт активные запросы до 55 с; общий grace period 70 с.

BAD имеет корректный хеш, но ready=false. Он остаётся вне Service, старые B
продолжают работу. Откат Helm выполняется к известной исправной ревизии A;
версия проверяется по ответам, а не values. Авария вызывается отдельным
локальным fault endpoint через os._exit(137), без graceful shutdown. Длинный
поток на этом процессе должен оборваться. Новые запросы и восстановление
контейнера фиксируются отдельно; клиентских повторов в генераторе нет.

Версия и диалог проверяются ещё раз после удаления Pod. Изоляция диалогов
проверяется разными контрольными строками. Сырые серверные логи сохраняются
через follow logs до удаления контейнеров; после рестарта — также previous.

## B — привязка и очередь

Гипотеза: 80% трафика через один IP при ClientIP перегружает одну реплику.
Исправление для стенда — обычный Service и отключённый keep-alive. Это
балансировка новых TCP-соединений, а не гарантия round-robin по HTTP-запросам.
Сохраняются kube-proxy mode, настройки Service, IP клиентов и IP в серверных
логах. Внутрикластерный путь не использует port-forward для рабочих запросов.

Сравнение: uniform/skew × plain/affinity × 3 повтора = 12 прогонов по 120 с
измерений каждый, 5 req/s, 12 частей ответа. Прогрев исключён из этой фазы.
В каждой паре одинаковы seed, payload, входные длины, ограничения, offset и
расписание. Порядок политик чередуется; кеш перед каждым прогоном пуст после
замены всех Pod. Набор подсказок имеет четыре повторяющихся префикса.
Сохраняются и случаи без ожидаемого перекоса: назначения клиентов могли
совпасть, часть трафика распределилась иначе, либо мощности оказалось достаточно.

Параметры имитатора: один одновременно обрабатываемый запрос/Pod, FIFO
asyncio.Semaphore, очередь 24, ожидание до 12 с; LRU на 16 префиксов, SHA256
первых 256 символов переданного контекста; hit 0,025 CPU-с, miss 0,2 CPU-с;
каждая часть 0,008 CPU-с, между частями 0,02 с. Кеш хранит только хеши и не
содержит пользовательского KV. Длительности CPU измеряются thread_time.
Предоставляемые значения — модель нагрузки, не характеристики Qwen.

Генератор open-loop, четыре процесса в разных Pod. Пишет planned и sent по
монотонным часам каждого клиента; wall epoch синхронизирует начало. При
перегрузке генератора не растягивает расписание: фиксирует generator_dropped.
Клиентские TCP-соединения не переиспользуются. Сравнивать p95 без числа
успехов, доли отказов, тайм-аутов и send lag запрещено.

## C — HPA и алерты

HPA autoscaling/v2: CPU requests=250m, цель 60%, min=2, max=3. Для наблюдаемой
CPU-причины cacheSize=0, miss=0,5 CPU-с и chunk=0,03 CPU-с, 12 req/s × 180 с.
Собираются resource metrics API, условия HPA, появление Pod, Ready, реальное
время возврата к 2 после завершения нагрузки. scaleDown stabilization=60 с,
но фактический возврат дольше из-за окна CPU, цикла контроллера и завершения Pod.

Повторный ClientIP-прогон: 80% через один IP, 8 req/s × 120 с. Средняя
утилизация способна вызвать scale-up, если превышает 60% requests; одна
горячая реплика может быть скрыта средним, если requests велики или соседние
реплики простаивают. Новая реплика при сохранённой affinity может почти не
получать трафик старых IP. Анализ требует трассы назначений, не только числа Pod.

Алерты: p95 TTFC >0,8 с и доля rejected|aborted >5%, минимум 30 наблюдений
за 1 минуту, for=30 с. Медленный прогон с очередью, затем перегрузка без очереди
дают два независимых условия; после — восстановление базовых параметров и
малой нагрузки. Сохраняются pending/firing и отсутствие активных алертов в конце.

## Формулы и сопоставление

TTFC = first_mono − sent_mono. Полная длительность = end_mono − sent_mono.
Inter-chunk latency — N−1 разностей времён получения N частей; для N=1
интервалов нет, среднее/перцентиль не определены. TTFT/TPOT/tokens/s не считаются:
реальных токенов модели здесь нет. Если подключается реальная модель, TTFT
измеряется до первого содержательного токена, TPOT=(t_last−t_first)/(N−1),
N считается закреплённым tokenizer; при N=1 TPOT=null.

Клиентские p50/p95: линейная интерполяция в сортированном массиве успешных
ответов. Серверная TTFC-гистограмма учитывает только завершённые успешные
ответы; обрывы идут отдельным счётчиком. Границы 0,01…51,2 с плюс +Inf.
PromQL хранит le при суммировании buckets. Для B снимаются накопительные
счётчики до и после изолированного прогона на неизменном наборе Pod;
analyze.py проверяет равенство количества успехов и интерполирует p95 из
разности buckets. Отличие от клиента объясняется сетевой доставкой и грубыми
границами; при несовпадении counts сравнение не считается подтверждённым.
