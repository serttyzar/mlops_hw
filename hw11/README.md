# ДЗ 11 — Kubernetes под нагрузкой

Продолжение `../hw8910`, в том же репозитории. Основной режим —
**backend_mode=simulated**, CPU; результаты имитатора не выдаются за Qwen.
Реальные веса и повторное обучение для обязательной части не нужны.

**Полный Kubernetes-прогон завершён успешно:** 15 812 результатов запросов,
29 Kubernetes-проверок, HPA 2→3→2, оба алерта и четыре графика. Итоговый
`report.html` находится в этой папке; фактические выводы — `docs/results.md`.
Сырые результаты: `results/terminal-20261115T212518Z-5488/`.
`verification.json`: complete=true, missing=[]. Ранее заблокированные и
неудачные попытки сохранены отдельно и не подменяют успешный прогон.

Ограничения MDM относятся к процессу агента; измерения выполнил предоставленный
локальный запускатель в обычном Terminal. Результаты относятся только к
CPU-имитатору.

## Что добавлено к предыдущей работе

- `app/backend.py` наследует прежний `hw8910.backends.StubBackend`: сохранён
  интерфейс `generate(prompt, limit)`. Сервис сохраняет JSON-контракт
  `POST /generate` (`prompt`, `max_new_tokens`) и добавляет `stream`, `messages`,
  `session_id`. Выдаёт части NDJSON с обязательным terminal frame `done`.
- CPU-вычисления выполняются в worker thread с `thread_time`, очередь и
  число активных запросов ограничены; локальный LRU явно имитирует prefix cache.
- Артефакты `artifacts/A.json`, `B.json`, `BAD.json` включены в образ, хеши
  закреплены в `sha256.json`. При запуске сверяются и хеш, и содержимое версии;
  некорректный файл блокирует readiness. BAD проверяет отказ прогрева.
- Helm: две реплики, обычный и ClientIP Service над одними Pod, ConfigMap,
  CPU/RAM requests/limits, startup/readiness/liveness, drain, HPA 2–3.
- Prometheus собирает каждый API Pod через Kubernetes discovery, cAdvisor и
  kube-state-metrics. Grafana dashboard и два алерта хранятся в chart/files.
- Генератор запускается в четырёх клиентских Pod, сохраняет расписание и
  реальные отправки. Сценарии A/B/C, проверки, четыре графика и HTML-отчёт
  формируются из настоящих записей, без подстановки демонстрационных данных.

## Запуск без изменения MDM-политики Codex

Откройте в Finder файл **`ЗапуститьДЗ11.command`** двойным щелчком.
Это обычный локальный скрипт пользователя для Terminal. Он не меняет MDM,
не выдаёт агенту новые права и не использует sudo. Его нельзя автоматически
запустить из ограниченного агента; открытие выполняет сам пользователь.

Скрипт использует готовый Python из предыдущего ДЗ либо отдельное окружение,
проверяет код, скачивает инструменты с проверкой хешей, запускает отдельную
Colima VM `mlops-hw11` (4 CPU, 6 GiB RAM, диски 8+12 GiB sparse), затем
сборку и все опыты. Глобальный Docker context и существующая Colima default
не меняются. Нужны доступные обычному Terminal интернет и виртуализация.
Если MDM ограничивает также эти возможности, скрипт сохранит причину отказа.

Результаты каждого запуска лежат в `results/terminal-<дата>-<pid>/`;
`results/LAST_RUN.txt` содержит последний путь, `launcher-status.json` — статус,
`launcher.log` — общий журнал. При сбое промежуточные результаты сохраняются,
на их основе формируется отчёт с указанием недостающих данных. После завершения
можно вернуться в чат: агент прочтёт результаты из файлов проекта.

До конца прогона оставьте окно Terminal открытым. Caffeinate предотвращает
автоматический сон во время работы; закрытая крышка может остановить Mac.
После окончания файл **`Остановить стенд ДЗ 11.command`** останавливает только
эту VM и освобождает её CPU/RAM, сохраняя результаты и образы.
Размер дисков sparse — верхний виртуальный предел, фактическое занятие меньше.
Для полного удаления VM после сохранения доказательств используется
`colima delete --profile mlops-hw11`; это удаляет только данный профиль.

## Локальные проверки

Python 3.12. В обычном терминале:

```sh
python3.12 -m venv .venv
.venv/bin/pip install -r requirements-report.txt
make check PYTHON=.venv/bin/python
```

Все runtime-зависимости, включая транзитивные, закреплены в requirements.txt.
Для текущей машины можно использовать готовое окружение прошлого ДЗ:

```sh
make check PYTHON=../hw8910/.venv/bin/python
```

Локальные проверки покрывают прогрев до/после, хеш и версию, неготовый артефакт,
восстановление состояния из клиентской истории, изоляцию, потоковый протокол,
ограничение и тайм-аут очереди, корректное завершение при disconnect и клиентский
учёт обрыва без terminal frame. Проверки Kubernetes находятся в cluster.py и
пишут отдельный `checks.jsonl`; они не заменяются этими тестами.

## Полный запуск Kubernetes

Нужен обычный терминал с доступом к Docker/Colima и интернету. Команды работают
только с отдельным кластером `mlops-hw11`, context `kind-mlops-hw11`, namespace
`hw11`. Kubeconfig хранится в `.state/kubeconfig`, глобальный context не меняется.

Перед первым запуском проверьте свободное место и лимиты VM. Бюджет:
**не менее 4 CPU, 6 GiB RAM, 8 GiB свободного диска**. Скрипт проверяет это до
создания стенда (для VM на 6 GiB требуется не менее 5,5 GiB доступной Docker RAM, с учётом памяти гостевой ОС). Если Colima уже используется другими задачами, изменяйте её
ресурсы с учётом этих задач; скрипт её не перезапускает и не перенастраивает.

```sh
make tools                         # только .tools, проверка опубликованных SHA256
export PATH="$PWD/.tools:$PATH"
make preflight PYTHON=.venv/bin/python
make experiments PYTHON=.venv/bin/python RESULTS=results/cluster-run1
make report PYTHON=.venv/bin/python RESULTS=results/cluster-run1
make verify PYTHON=.venv/bin/python RESULTS=results/cluster-run1
```

`experiments` включает сборку образа, kind, metrics-server, Helm и все опыты.
Занимает ориентировочно 40–60 минут, из них B — 12 фаз по 120 с плюс прогрев
и завершение очереди. Используйте новую папку RESULTS для нового полного запуска:
повтор в старую папку добавляет журналы и не считается независимым запуском.
Отдельная отладка после `make setup`:

```sh
.venv/bin/python scripts/cluster.py A --output results/debug-A
.venv/bin/python scripts/cluster.py B --output results/debug-B
.venv/bin/python scripts/cluster.py C --output results/debug-C
```

Скрипт останавливается на проваленной проверке, сохраняя исходные данные.
Один неожиданный результат балансировки сам по себе не вызывает повтор:
он сохраняется и должен быть объяснён по распределению клиентов и состоянию Pod.
Сетевые тайм-ауты и отказы считаются отдельно, клиентских повторов нет.

Просмотр мониторинга после запуска (два терминала):

```sh
export KUBECONFIG="$PWD/.state/kubeconfig"
kubectl --context kind-mlops-hw11 -n hw11 port-forward svc/hw11-grafana 3000:3000
kubectl --context kind-mlops-hw11 -n hw11 port-forward svc/hw11-prometheus 9090:9090
```

Grafana: http://127.0.0.1:3000, dashboard `HW11 · CPU simulation`, доступ Viewer.
Prometheus: http://127.0.0.1:9090. Рабочая нагрузка идёт из Pod через Service,
port-forward используется только для мониторинга и считывания метрик.

## Закреплённые версии и бюджет хранения

| Компонент | Версия / ограничение |
|---|---|
| Python в образе | 3.12.12-slim-bookworm |
| kind / Kubernetes | 0.27.0 / kindest/node:v1.32.2 |
| kubectl / Helm | 1.32.2 / 3.16.4 |
| metrics-server | 0.7.2; insecure kubelet TLS только для локального kind |
| Prometheus / Grafana | 3.2.1 / 11.6.0 |
| kube-state-metrics | 2.15.0 |
| API / Pod | requests 250m CPU, 96Mi; limits 1 CPU, 256Mi |
| Prometheus | limits 500m/384Mi; retention 2h и 256 MB; emptyDir ≤512Mi |
| Grafana | limits 300m/256Mi; emptyDir ≤128Mi |
| Клиент / Pod, 4 шт. | limits 500m/192Mi; emptyDir ≤128Mi каждый |
| Модели | три небольших JSON в образе; внешних весов и PVC нет |

Теги образов закреплены версиями; фактические image ID/digest и Kubernetes/node
версии сохраняются при запуске. Ожидаемый добавочный Docker-бюджет 3–6 GiB с
kind node и образами мониторинга, верхний рабочий резерв 8 GiB. Это оценка,
фактический размер доступен только после сборки: `environment-before.json`,
`image.json`, `size-after.txt`. Размер исходников сохраняется отдельно в
`results/local/source-size.json`; он не является размером Kubernetes-стенда.

В репозитории нет весов, .venv, Docker-дисков или токенов. Логи и результаты
полного прогона нужно добавить в Git явно после проверки их размера.

## Отчёт и сдача

`docs/experiments.md` — гипотезы, исходные дефекты, изменения, условия, формулы,
ограничения и приёмка. `docs/review.md` — письменное ревью с кейсом Google из
лекции и первичным источником. Главы видео и релевантные кадры — `docs/lecture`.

В `results/cluster-run1/` сохраняются `requests.jsonl`, расписания, логи клиентов
и API Pod, Ready/EndpointSlice/HPA timeline, конфигурация сети, снимки счётчиков
Prometheus, `checks.jsonl`, `summary.json`, `verification.json` и четыре SVG.
`report.html` встраивает графики, поэтому переносится одним файлом. Если каких-то
данных нет, отчёт это отмечает, а verify возвращает ненулевой код.

Перед сдачей выполните все четыре команды experiments/report/verify/check,
добавьте результаты в существующий репозиторий и укажите URL и **коммит,
содержащий фактический успешный прогон**. Коммит только с кодом не доказывает
выполнение измерительной части. Наличие прежнего remote не означает, что новое
ДЗ уже опубликовано.

## Удаление собственного стенда

Сначала сохраните результаты на хосте. Удаление kind удаляет также ephemeral
метрики и клиентские файлы. Скрипт удаляет только свой кластер и API-образ:

```sh
make cleanup PYTHON=.venv/bin/python
```

Эквивалентные команды:

```sh
kind delete cluster --name mlops-hw11
docker image rm hw11-api:0.1.0
```

Скачанные общие образы остаются в кеше Docker. Если они больше не используются,
их можно удалить отдельно по точным тегам из values.yaml и kindest/node:v1.32.2.
Общий `docker system prune` не нужен и в скриптах не используется.

## Проверка сохранённой сдачи из чистой копии

Полные сырые события опубликованы как `events.jsonl.gz`: это сжатие gzip без
потери данных, SHA256 до/после распаковки совпадает. Хеши и исходный размер
записаны в `evidence-manifest.json`. `requests.jsonl` оставлен без сжатия.
Скрипты проверки и построения отчёта читают оба формата автоматически;
оригинальный events.jsonl остаётся локально и исключён из Git из-за размера.

```sh
python3 scripts/verify_evidence.py results/terminal-20261115T212518Z-5488
```

Эта проверка использует только стандартную библиотеку и не требует запущенного
Kubernetes. Для пересоздания графиков нужно окружение из requirements-report.txt.
Все данные успешного прогона включены в сдачу; скачанные инструменты,
виртуальные окружения, kubeconfig и неудачные попытки в неё не входят.

Коммит с полной сдачей: [a490e56](https://github.com/serttyzar/mlops_hw/commit/a490e568be55cd3bc76265b85e22ede3ac2ce25b).

## Публикация из обычного Terminal

Если сеть агента ограничена MDM, откройте `ОпубликоватьДЗ11.command`.
Он отправляет уже созданные коммиты обычным `git push origin main`,
не добавляет изменения старых ДЗ и не использует force push. Сравнивает
SHA локального main с ответом `git ls-remote`; подтверждение записывает
в `results/publish-status.json`, журнал — в `results/publish.log`.
Используются только уже настроенные учётные данные Git. Опыты не повторяются.

Проверить подготовку публикации без сетевого обращения можно командой
`bash ./ОпубликоватьДЗ11.command --check-only`. Имена файлов читаются через
NUL-разделители, включая кириллицу и пробелы.
